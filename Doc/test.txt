GitHub Flow 只有 main + 短生命周期功能分支：从 main 开分支 → 提 PR → 评审 + CI → 合入 → 部署。规则少、心智负担低，是大多数团队的合理起点。

项目管理原则
1、一个main分支，始终保持能正常运行。
2、开发新功能必须先从main拉取最新版本，然后开新分支，完成功能后提交分支，并申请合并到main。提交信息简单规范“feat: 新功能，fix: 修 bug，docs: 改文档，refactor: 重构”。
注：一个 PR 只做一件事：别把新功能、修 bug、重构混在一起。分支尽量短命：做完就合，别放几周，越久冲突越多。PR 描述写三件事：改了什么、为什么改、怎么测试。
3、提交的PR由专人审核并测试后完成合并。
4、一定做好可扩展性，模块之间通过公开函数、事件、ScriptableObject 通信，少用单例硬引用。这会让后续开发事半功倍。
5、一般情况下，不允许修改非自己任务部分的代码，尽量让每个模块之间独立。改别人模块前先沟通：不是绝对禁止，但必须先说一声，避免互相覆盖。
6、配置数据驱动：设备参数、点位映射放配置文件，别写死在代码里。
